# Badger 介绍
Badger 是一个用 Go 写的高性能嵌入式 Key-Value 数据库。
### 1.嵌入式
不需要启动服务，直接在 Go 代码里用
你的程序 → 调用 DuckDB / Badger → 直接读写文件
不需要 MySQL / Redis 那种独立进程
没有网络开销
### 2.很快（LSM Tree）
底层用： LSM Tree
特点：
- 写入非常快（顺序写）
- 适合大量数据

LSM Tree ：先写入内存，再顺序写入磁盘，并通过后台不断合并整理数据的存储结构。它通过把随机写变成顺序写来大幅提升写入性能，适合写多读少的场景，但代价是读时需要查多层数据（读放大）以及后台合并带来的开销。
LSM Tree ：先写内存 → 再顺序写磁盘文件 → 最后后台不断归并整理多个磁盘文件。
完整流程：
`写入 →
1. 写 WAL（防止丢数据）
2. 写 MemTable（内存）
   ↓
   内存满了 →
3. flush 成 SSTable（磁盘文件）
   ↓
   后台 →
4. Compaction（归并整理）`

LSM Tree 通过将随机写转换为顺序写，大幅提升写入性能，因此非常适合写密集场景。但由于数据分布在多层结构中，读取时需要查询多个位置，同时还存在后台 compaction 开销，因此读性能相对较弱，更适用于写多读少的场景。
LSM Tree的读放大：由于写入采用追加方式，旧数据不会立即删除，导致同一个 key 可能分布在内存和多个层级的 SSTable 中，因此读取时需要从上到下逐层查找

### Badger 和 duckdb的区别：前者是kv数据库， 后者是sql数据库

# BoltDB 介绍
etcd = Raft + BoltDB
BoltDB 使用 B+Tree 结构（读稳定）
etcd 场景是： 配置中心，服务发现 --> 读多写少
读为什么强：
- B+Tree 是一棵有序多叉树 时间复杂度：O(log N)
- 磁盘访问次数很少 3 ~ 4 次磁盘 IO 就能找到数据
- 叶子节点是链表 支持 范围查询，排序扫描
写为什么弱：
- 随机 IO ：写入时需要定位到具体的磁盘页并进行修改，而这些页在磁盘上的位置是离散的，因此每次写入都会跳转到不同位置，属于随机 IO
- 可能发生“页分裂” ： 需要额外写多个页，所以产生了写放大
- 
| 特性 | B+Tree     | LSM Tree        |
| -- | ---------- | --------------- |
| 写  | ❌ 慢（随机 IO） | ✅ 快（顺序写）        |
| 读  | ✅ 快且稳定     | ❌ 可能慢（多层查）      |
| 延迟 | 稳定         | 有抖动（compaction） |
